## 単一実行ファイルのバンドル JS を文字列走査して挙動を確定する

ツールの挙動が推測でしか語れないとき、**バンドルされた実行ファイルから該当箇所を読み出して事実にする**手法。2026-08-04 に Claude Code の `Hook cancelled` の原因特定で使い、既定タイムアウト値（1500ms）とプラグイン由来フックが予算計算から除外される事実を**推測ではなく引用として**確定できた（[[Gotchas]]）。

手順:

1. **エラー文言をそのまま検索キーにする**。`claude.exe`（265 MB）のような巨大バイナリでも、UTF-8 バイト列としてチャンク走査すれば数十秒でオフセットが出る。チャンク境界をまたぐ一致を落とさないよう、前チャンク末尾を needle 長ぶん持ち越すこと。
2. **オフセット周辺 ±1.5〜2.5 KB をダンプして読む**。Bun/esbuild 系の単一バイナリは JS ソースがほぼ素のまま埋まっているため、minify 後でも制御フローは追える。
3. **文字列テーブル領域とコード領域を見分ける**。同じ文言が複数オフセットで当たるが、区切り文字が並ぶだけの領域は定数プールで、関数定義が読めるのはコード領域。後者だけ読めばよい。
4. **定数の実値まで辿る**。`$2o=1500` のような minify 後の識別子は、定義側（`var …=1500,…`）を別途検索して値を確定する。

適用条件と限界:

- **バージョンに強く依存する**。読んだ結果は必ず版数とセットで記録する（例: `claude.exe` v2.1.220）。更新で識別子も定数も変わる。
- **公式ドキュメントに書かれていない既定値・優先順位・除外条件**を知りたいときにだけ使う。ドキュメント化されている事項は素直にそちらを見る。
- 挙動の**再現実測とセットにする**。今回も「予算 1500ms」という読み取りと「フック実測 ~500ms」という計測の両方があって初めて「余裕3倍しかない」と言えた。片方だけでは断定できない。

## enforcement ruleは「違反を検知できること」自体を検証する（2026-09-06）

[[TECSCDE-DT-EL実装]]でdependency-cruiserの禁止importルール（`renderer/`から`electron`への禁止）を書いた際、最初の実装は`to.path`が npm パッケージの**生の指定子**（`"electron"`）にマッチしており、実際の解決済みパス（`"node_modules/electron/index.js"`）と食い違って**常に無検知のまま素通り**していた——ルールを書いて「エラーが出ない」ことを確認しただけでは、ルールが機能しているのか単に何も検知していないだけなのか区別できない。

- **一般化**: lint設定・CIゲート・dependency-cruiser等の「静的に強制するルール」全般に適用できる——ルールのテストなしに「エラーが出ないこと」を「ルールが機能していること」の証拠にしない。

## 依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）

[[TECSCDE-DT-EL実装]]のpreload契約テストは`vi.mock("electron", ...)`でElectronをモックし、TSソースをvitestが変換して読む。47テストが全pass・`npm run check` greenでも、実機`electron .`起動で**2段のエラーが連続して露見**した: ①preloadの`.js`出力がESMだがElectronのサンドボックス化preloadはCommonJSで実行される（`SyntaxError: Cannot use import statement outside a module`） ②ESM化後、`import { clipboard } from "electron"`が通らない（ESMの`electron`はpreload向けにclipboardを名前付きエクスポートしない）。どちらも「モックの向こう側」＝ビルド出力形式・ホストランタイムのモジュール解決という、モックが覆い隠す層にあった。

- **対処**: プロセス境界・ネイティブホスト（Electron/Tauri/ブラウザ拡張のservice worker等）を持つプロジェクトでは、契約テストの緑とは別に「実際にホストで起動して1回ロードさせる」スモークテストを最初の検証単位に含める（内部仕様11.4節#2が「UIより先にIPCゲートウェイ疎通を確認」としていたのは正しい方向だったが、"疎通"を契約テストで代用していた分だけ穴が残った）。
- **一般化**: モックはユニットの論理を速く回すための道具であって、統合点の検証にはならない。モック境界＝検証の死角、と考える。

## パッケージング境界（asar化）は、開発時の起動確認とは別の検証点になる（2026-09-15）

[[TECSCDE-DT-EL実装]]で「`electron .`での起動確認は緑」→「`electron-forge package`でasar化した`.exe`は起動直後にクラッシュ」が発生。上記2026-09-08の教訓（契約テストの緑は実機統合を保証しない）と同じ構造が、**開発時起動と本番パッケージの間**にもう一段存在することが分かった。

**症状**: `out\tecscde-dt-el-win32-x64\tecscde-dt-el.exe`を起動すると`Error: Cannot find module 'electron-squirrel-startup'`。`electron .`では問題なく動いていたコードが、パッケージ化した瞬間に落ちる。

**原因**: `electron-squirrel-startup`が`package.json`の`devDependencies`に入っていた。開発時（`electron .`）はプロジェクト全体の`node_modules`がそのまま見えるため気づかないが、Electron Forgeのpackagerはasar化時に`devDependencies`をプルーニングして`node_modules`を作るため、実行時にモジュールが存在しなくなる。preload自体のESM/asar互換性（当初警戒していたリスク）は実際には無関係だった。

**検証手順（確立）**:
1. `npm run forge:package`（または`forge:make`）でasar化された実行ファイル一式を生成
2. **ターミナルから直接起動**（エクスプローラーからのダブルクリックではなくコンソールから）してmainプロセスの標準出力/エラーを見る——`Cannot find module`や`Unable to load preload script`はここで検知できる
3. DevTools Console（`Ctrl+Shift+I`、出なければ一時的に`webContents.openDevTools()`を仕込む）で`window.<preloadが公開するAPI名>`が存在するか確認し、実際のAPIを1つ叩いてIPC往復まで確認する
4. 任意で`npx asar list <app.asar> | grep <対象ファイル>`でasar内にファイル自体が含まれているかを見る——ただし**これは「含まれている」ことの確認に過ぎず「実行時に解決・ロードできる」ことの証拠にはならない**（今回もpreloadファイル自体はasar内に存在したが、無関係な依存関係の欠落でその手前でクラッシュしていた）

**一般化**: 「dev起動」「package」「make（インストーラ経由）」はそれぞれ`node_modules`の内容・ファイルパス解決・実行コンテキストが異なりうる別々の検証境界であり、一つが緑でも次の境界特有の失敗（依存関係のプルーニング、パス解決の変化、署名・権限の違いなど）を隠す。**出荷する形態（この場合はpackage/make後の実行ファイル）でこそ最終検証を行う**——[[Patterns - 検証と調査 Archive#依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）|モックが覆い隠す層]]と同型の「検証の環が系の内側で閉じる」失敗。
- **出典**: 2026-09-15セッション、[[work/active/TECSCDE-DT-EL実装/TECSCDE-DT-EL実装]] Action Items、[[work/active/tecs/TECSCDE-DT-EL preload ESM・sandbox決定]]

## shardmind をクロバーなしで更新する（2026-09-09）

`shardmind update` は手動 CLI（cron・hook・mise タスクいずれも呼んでいない。SessionStart がやるのは更新*チェック*だけ）。v8.4.0 更新で地元カスタマイズが広範に巻き戻された（詳細と復旧は [[Gotchas - Git & Vault Integrity#shardmind の更新は managed ファイルを再レンダーして地元のカスタマイズを巻き戻す]]）。二度踏まないための手順:

- **更新前**:
  1. 作業ツリーを完全にクリーンにする（`git status --porcelain` が空）。更新差分を `git diff HEAD` だけで読めて、`git checkout HEAD -- <file>` で個別に戻せる状態にしておく。
  2. `shardmind --verbose --no-update-check` で "modified by you" 一覧を確認。**自分で編集したのにここに出ていないファイル**（`managed` のまま）は無防備 → 先に `.shardmind/state.json` でそのエントリを `"ownership": "modified"` にする。
  3. `shardmind update --dry-run --json` で per-file プランを確認。CHANGELOG と照合し「本当のペイロード」と「巻き添えの再レンダー」を切り分ける。
- **更新実行**: 必ず対話 TUI（`shardmind update`）。`--yes` は "auto-keeps conflicts" だが非対話で全ファイルを流すので事故のもと。3-way マージが衝突したら TUI が選択を求める。
- **更新後・コミット前**: `git diff HEAD` 全レビュー → `.shardmind/backups/update-<timestamp>/files/`（更新前スナップショット、gitignore 済み）と突き合わせ → 巻き添えの内容欠損は `git checkout HEAD -- <file>` で戻し、戻したファイルは `.shardmind/state.json` で `"ownership": "modified"` に固定 → `cd .claude/scripts && npm test`。
- **構造的対策**: `AGENTS.md` / `GEMINI.md` / `Home.md` / `perf/Brag Doc.md` / `org/People & Context.md` のような「テンプレ管理下なのに内容が育つ」ファイルは、追記分を別ノートに切り出してリンクし、管理ファイル本体をテンプレに近い状態に保つと 3-way マージの衝突自体が起きなくなる。2026-09-09 時点で 16 ファイルを `ownership: modified` に固定済み（`shardmind --verbose` で確認可能）。
- **出典**: 2026-09-09 セッション、コミット `c65af14`〜`fc73cf5`（各メッセージに詳細）

## 自前パーサと自前シリアライザのround-tripは、方言が外界の仕様から外れていても永久に緑になる（2026-09-13）

[[TECSCDE-JS-TS実装]]でCDLパーサをtree-sitter（tecsgenの構文定義`bnf.y.rb`からの移植文法）へ差し替えた際に判明。

**症状**: 手書きパーサが受理していたのは実際のCDLではなく、本ツール独自の方言だった——`entry_port`（実際は`entry`）、`attribute name;`（実際は`attr { int32_t name; };`）、`cell tFoo c1 { }`（実際は終端`;`が必要）、`import "x";`（実際は`import("x");`）。つまり**本ツールが保存した`.cde`はtecsgenに入力できなかった**。外部仕様2.2「tecsgenが受理するCDLを入出力対象とする」への違反が、実装当初から検出されないまま残っていた。

**なぜ検出できなかったか**: round-tripテスト（読み込み→保存→再読み込みで一致すること）は**パーサとシリアライザが同じ方言を共有していれば常に緑になる**。両者は互いに整合しており、系の外側にある本物の文法とは一度も突き合わせていなかった。fixtureも同じ方言で書かれていたため、テストは系の内部だけで閉じていた。実装ノートには「tecsgen本来の文法ではなく、検証に必要な範囲の**サブセット**」と書かれていたが、実態はサブセットではなく**別方言**だった——この取り違えが、問題を「既知の制限」に見せていた。

**対処**: 出力を系の外にある正典（tecsgen自身の構文定義から生成したパーサ）に通し、`ERROR`/`MISSING`がゼロであることをテストで固定した。fixtureも本物のCDLへ書き換えた。

**一般化**: 入力と出力を同じ自作コードで扱う系（パーサ/シリアライザ、エンコーダ/デコーダ、シリアライズ形式の読み書き）では、**round-tripは自己整合性しか測らない**。「外界の実装が受理するか」は別の検証軸として明示的に持つ必要がある。[[Patterns - 検証と調査 Archive#依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）|モックした契約テストが実ランタイム統合を検証しない]]のと同じ構造——検証の環が系の内側で閉じている。

## 他言語の一次資料を実際に読んで、仕様書の「inferred・未検証」フラグを解消する（2026-09-22）

## テスト作成そのものが、設計書の擬似コードに埋め込まれたバグを検出する（2026-09-22）

[[work/active/TECSCDE-DT-EL内部仕様/TECSCDE-DT-EL内部仕様 - 07C 読み込み経路の統合|第7C章]]#8/#10の実装で、設計書の擬似コード（いずれも「実装時に確定」と明記されていた）を実際に動くコードへ落とす過程で、擬似コード自体に2つの欠陥が見つかった——(1) `loadOptionsFile`が`addAsReference`を`openFromPath`より先に呼ぶ順序になっていたが、`addAsReference`は「既存の編集対象」を前提とする実装のため前の編集対象に参照が誤って付く、(2) `.tecsgen-opts`ファイル中のCDLパスは相対パス想定だが、`.tecsgen-opts`自身のディレクトリを基点に解決する処理が欠けていた。後者はテストを書いて実行した際に`main.cde`ではなく`"main.cde"`（相対のまま）がgatewayへ渡っていることに気づいて発覚した。

**一般化**: 設計書の擬似コードは「関数名と大まかな処理順」を示すのに向くが、**呼び出し順序の前提（何が確定していないと成立しないか）や相対パスの基点**のような細部は、実際にテストを書いて実行するまで検証されない。「実装時に確定」と明記された箇所は、レビューだけでなく**動くテストを1つ書く**まで疑ってよい——[[Patterns - 検証と調査 Archive#依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）|モックした契約テスト]]と対になる教訓で、あちらは「モックが実環境の壊れを隠す」、こちらは「テストを書く行為自体が設計の欠陥を暴く」。

## 配布・CI設計は、対象環境の実際の権限・可視性を実装前に確認してから確定する（2026-09-23）

[[work/active/tecs/TECSCDE-DT-EL 配布アーキテクチャ決定|TECSCDE-DT-EL配布アーキテクチャ決定]]で、`update-electron-app` + GitHub Releasesという設計方針をユーザーと確認して固めた直後、実リポジトリ（`E:\Ccur\typescript\TECSCDE-DT-EL`）のpush先`origin`を`git remote -v`・`gh repo view`で確認したところ**非公開**と判明し、既定の自動更新サービスがそのままでは機能しないことが分かった。設計の合意自体はコードを見る前の会話だけで成立してしまうため、この種の制約（リポジトリ可視性・権限・認証スコープ）は実装に入る直前に一度、実環境に対してコマンドで確認するまで顕在化しない。

**一般化**: 配布・CI/CD・認証まわりの設計は、要件レベルの合意（「GitHub Releasesで配る」）だけでなく、**その合意が成立する前提条件（可視性・権限・スコープ）を対象環境に対して実際に問い合わせてから確定する**——`gh repo view`・`git remote -v`のような数秒のコマンド1つで、設計の手戻りを避けられる。この教訓は[[Patterns - 検証と調査 Archive#依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）|モックした契約テスト]]・[[Patterns - 検証と調査 Archive#他言語の一次資料を実際に読んで、仕様書の「inferred・未検証」フラグを解消する（2026-09-22）|一次資料を読む]]と同じ「推測ではなく実環境への問い合わせで確定する」構えを、コードの挙動ではなく**インフラ・権限設定**にまで広げたもの。なお本件は同日中にユーザーがorigin可視性を変更したことで解決し、設計を単純化する側へ再確定できた——早期発見が手戻りを最小化した例（[[brain/Gotchas - Tooling & Config#テンプレート由来の `.gitignore` が `.github/` を丸ごと除外し、GitHub Actionsが一切コミットできない|関連gotcha]]も同セッションの副産物）。

## Ruby構造解析は正規表現の行走査でなくAST（`RubyVM::AbstractSyntaxTree`）を使う（2026-09-24）

[[work/active/tecsgen/tecsgen内部仕様|tecsgen（Ruby実装）]]の「トップレベルで定義された全メソッド」を全数調査した際、最初は`class`/`module`/`def`/`end`等のキーワードを行単位の正規表現でスタック管理する簡易パーサーを書いた。結果、374個ものメソッドを「トップレベル」と誤検出——原因は`tecslib/core/bnf.tab.rb`（raccが`bnf.y.rb`から生成した構文解析器）で、328個の`_reduce_N`メソッドが`Parser.module_eval(<<HEREDOC)`というヒアドキュメント文字列の中に書かれていたこと。行走査はヒアドキュメントの中身もただのテキストとして読むため、実際には文字列リテラルの一部でしかない`def _reduce_10(...)`を本物の定義と誤認した。Rubyがインストール済み（`ruby 4.0`）だったため、`RubyVM::AbstractSyntaxTree.parse(src)`でASTを構築し、`:CLASS`/`:MODULE`/`:SCLASS`ノードの子孫かどうかで判定し直したところ、正しく23個まで絞り込めた——ヒアドキュメントは文字列ノードの中に閉じ込められ、そもそも`:DEFN`ノードとして現れないため、この種の誤検出が構造的に起きない。

**一般化**: 「対象言語の構造（ブロックのネスト、スコープ）を正確に判定する必要がある」タスクでは、正規表現の行走査は**文字列リテラル・ヒアドキュメント・コメントの中身と実コードを区別できない**という構造的な弱点を持つ。対象言語の処理系がその場で使えるなら（`ruby`コマンドが入っている、等）、自作の簡易パーサーより先に、言語組み込みのAST/パーサー（Rubyなら`RubyVM::AbstractSyntaxTree`や`Ripper`、他言語ならそれぞれの標準パーサーライブラリ）を使えないか確認する。正規表現ベースの結果は「怪しい候補の一次選抜」までに留め、最終成果物として確定させる前に処理系ベースの検証を挟む。
