## 単一実行ファイルのバンドル JS を文字列走査して挙動を確定する

ツールの挙動が推測でしか語れないとき、**バンドルされた実行ファイルから該当箇所を読み出して事実にする**手法。2026-08-04 に Claude Code の `Hook cancelled` の原因特定で使い、既定タイムアウト値（1500ms）とプラグイン由来フックが予算計算から除外される事実を**推測ではなく引用として**確定できた（[[Gotchas]]）。

手順:

1. **エラー文言をそのまま検索キーにする**。`claude.exe`（265 MB）のような巨大バイナリでも、UTF-8 バイト列としてチャンク走査すれば数十秒でオフセットが出る。チャンク境界をまたぐ一致を落とさないよう、前チャンク末尾を needle 長ぶん持ち越すこと。
2. **オフセット周辺 ±1.5〜2.5 KB をダンプして読む**。Bun/esbuild 系の単一バイナリは JS ソースがほぼ素のまま埋まっているため、minify 後でも制御フローは追える。
3. **文字列テーブル領域とコード領域を見分ける**。同じ文言が複数オフセットで当たるが、区切り文字が並ぶだけの領域は定数プールで、関数定義が読めるのはコード領域。後者だけ読めばよい。
4. **定数の実値まで辿る**。`$2o=1500` のような minify 後の識別子は、定義側（`var …=1500,…`）を別途検索して値を確定する。

適用条件と限界:

- **バージョンに強く依存する**。読んだ結果は必ず版数とセットで記録する（例: `claude.exe` v2.1.220）。更新で識別子も定数も変わる。
- **公式ドキュメントに書かれていない既定値・優先順位・除外条件**を知りたいときにだけ使う。ドキュメント化されている事項は素直にそちらを見る。
- 挙動の**再現実測とセットにする**。今回も「予算 1500ms」という読み取りと「フック実測 ~500ms」という計測の両方があって初めて「余裕3倍しかない」と言えた。片方だけでは断定できない。

## 実装前にリポジトリの実態を確認する（2026-09-06、2件目の発生）

vaultのノートが「着手前」「実装は存在しない」と記載していても、実際のローカルリポジトリでは既に実装・テストが進んでいることがある——ノート更新を伴わずに実装が進む（またはセッションをまたいで忘れられる）ため。

- **1件目（2026-09-01）**: [[TECSCDE-JS-TS実装]]で`MoveJoinBarCommand`の実装を依頼されたが、着手前に`E:\Ccur\typescript\TECSCDE`を確認したところモデル層〜テスト8件まで一気通貫で実装済みと判明（作成者・セッション不明）。
- **2件目（2026-09-06）**: [[TECSCDE-DT-EL実装]]の作業で[[TECSCDE-TS実装]]のmodel/cdlを移植しようとした際、ノートは「着手前（実装・テストは一切存在しない）」と記載していたが、`E:\Ccur\typescript\TECSCDE-TS`には実際に`initial commit`（8テストpass）が存在していた。
- **教訓（2回目で確定）**: 実装作業（特に「既存実装を移植・参照する」タスク）の着手前には、vaultのノートを鵜呑みにせず**対象ローカルリポジトリで`git log`・テスト実行を直接確認する**。ノート側は気づいた時点でsingle-source-status原則に沿って訂正する（本件では[[TECSCDE-TS実装]]のdescription・Notes・Action Itemsを訂正）。
- **出典**: [[Memories]] 2026-09-01・2026-09-06エントリ

## enforcement ruleは「違反を検知できること」自体を検証する（2026-09-06）

[[TECSCDE-DT-EL実装]]でdependency-cruiserの禁止importルール（`renderer/`から`electron`への禁止）を書いた際、最初の実装は`to.path`が npm パッケージの**生の指定子**（`"electron"`）にマッチしており、実際の解決済みパス（`"node_modules/electron/index.js"`）と食い違って**常に無検知のまま素通り**していた——ルールを書いて「エラーが出ない」ことを確認しただけでは、ルールが機能しているのか単に何も検知していないだけなのか区別できない。

- **対処**: ルール追加のたびに、一時的に違反コードを注入して「検知されること」を確認してから元に戻す（テストで言うRED→GREENの確認と同型）。本件ではこの確認を行ったことで初めてバグに気づいた。
- **一般化**: lint設定・CIゲート・dependency-cruiser等の「静的に強制するルール」全般に適用できる——ルールのテストなしに「エラーが出ないこと」を「ルールが機能していること」の証拠にしない。
- **出典**: [[Memories]] 2026-09-06エントリ、`E:\Ccur\typescript\TECSCDE-DT-EL\.dependency-cruiser.cjs`

## 依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）

[[TECSCDE-DT-EL実装]]のpreload契約テストは`vi.mock("electron", ...)`でElectronをモックし、TSソースをvitestが変換して読む。47テストが全pass・`npm run check` greenでも、実機`electron .`起動で**2段のエラーが連続して露見**した: ①preloadの`.js`出力がESMだがElectronのサンドボックス化preloadはCommonJSで実行される（`SyntaxError: Cannot use import statement outside a module`） ②ESM化後、`import { clipboard } from "electron"`が通らない（ESMの`electron`はpreload向けにclipboardを名前付きエクスポートしない）。どちらも「モックの向こう側」＝ビルド出力形式・ホストランタイムのモジュール解決という、モックが覆い隠す層にあった。

- **対処**: プロセス境界・ネイティブホスト（Electron/Tauri/ブラウザ拡張のservice worker等）を持つプロジェクトでは、契約テストの緑とは別に「実際にホストで起動して1回ロードさせる」スモークテストを最初の検証単位に含める（内部仕様11.4節#2が「UIより先にIPCゲートウェイ疎通を確認」としていたのは正しい方向だったが、"疎通"を契約テストで代用していた分だけ穴が残った）。
- **一般化**: モックはユニットの論理を速く回すための道具であって、統合点の検証にはならない。モック境界＝検証の死角、と考える。
- **出典**: [[Memories]] 2026-09-08エントリ、[[work/active/tecs/TECSCDE-DT-EL preload ESM・sandbox決定]]

## shardmind をクロバーなしで更新する（2026-09-09）

`shardmind update` は手動 CLI（cron・hook・mise タスクいずれも呼んでいない。SessionStart がやるのは更新*チェック*だけ）。v8.4.0 更新で地元カスタマイズが広範に巻き戻された（詳細と復旧は [[Gotchas - Git & Vault Integrity#shardmind の更新は managed ファイルを再レンダーして地元のカスタマイズを巻き戻す]]）。二度踏まないための手順:

- **更新前**:
  1. 作業ツリーを完全にクリーンにする（`git status --porcelain` が空）。更新差分を `git diff HEAD` だけで読めて、`git checkout HEAD -- <file>` で個別に戻せる状態にしておく。
  2. `shardmind --verbose --no-update-check` で "modified by you" 一覧を確認。**自分で編集したのにここに出ていないファイル**（`managed` のまま）は無防備 → 先に `.shardmind/state.json` でそのエントリを `"ownership": "modified"` にする。
  3. `shardmind update --dry-run --json` で per-file プランを確認。CHANGELOG と照合し「本当のペイロード」と「巻き添えの再レンダー」を切り分ける。
- **更新実行**: 必ず対話 TUI（`shardmind update`）。`--yes` は "auto-keeps conflicts" だが非対話で全ファイルを流すので事故のもと。3-way マージが衝突したら TUI が選択を求める。
- **更新後・コミット前**: `git diff HEAD` 全レビュー → `.shardmind/backups/update-<timestamp>/files/`（更新前スナップショット、gitignore 済み）と突き合わせ → 巻き添えの内容欠損は `git checkout HEAD -- <file>` で戻し、戻したファイルは `.shardmind/state.json` で `"ownership": "modified"` に固定 → `cd .claude/scripts && npm test`。
- **構造的対策**: `AGENTS.md` / `GEMINI.md` / `Home.md` / `perf/Brag Doc.md` / `org/People & Context.md` のような「テンプレ管理下なのに内容が育つ」ファイルは、追記分を別ノートに切り出してリンクし、管理ファイル本体をテンプレに近い状態に保つと 3-way マージの衝突自体が起きなくなる。2026-09-09 時点で 16 ファイルを `ownership: modified` に固定済み（`shardmind --verbose` で確認可能）。
- **出典**: 2026-09-09 セッション、コミット `c65af14`〜`fc73cf5`（各メッセージに詳細）

## 自前パーサと自前シリアライザのround-tripは、方言が外界の仕様から外れていても永久に緑になる（2026-09-13）

[[TECSCDE-JS-TS実装]]でCDLパーサをtree-sitter（tecsgenの構文定義`bnf.y.rb`からの移植文法）へ差し替えた際に判明。

**症状**: 手書きパーサが受理していたのは実際のCDLではなく、本ツール独自の方言だった——`entry_port`（実際は`entry`）、`attribute name;`（実際は`attr { int32_t name; };`）、`cell tFoo c1 { }`（実際は終端`;`が必要）、`import "x";`（実際は`import("x");`）。つまり**本ツールが保存した`.cde`はtecsgenに入力できなかった**。外部仕様2.2「tecsgenが受理するCDLを入出力対象とする」への違反が、実装当初から検出されないまま残っていた。

**なぜ検出できなかったか**: round-tripテスト（読み込み→保存→再読み込みで一致すること）は**パーサとシリアライザが同じ方言を共有していれば常に緑になる**。両者は互いに整合しており、系の外側にある本物の文法とは一度も突き合わせていなかった。fixtureも同じ方言で書かれていたため、テストは系の内部だけで閉じていた。実装ノートには「tecsgen本来の文法ではなく、検証に必要な範囲の**サブセット**」と書かれていたが、実態はサブセットではなく**別方言**だった——この取り違えが、問題を「既知の制限」に見せていた。

**対処**: 出力を系の外にある正典（tecsgen自身の構文定義から生成したパーサ）に通し、`ERROR`/`MISSING`がゼロであることをテストで固定した。fixtureも本物のCDLへ書き換えた。

**一般化**: 入力と出力を同じ自作コードで扱う系（パーサ/シリアライザ、エンコーダ/デコーダ、シリアライズ形式の読み書き）では、**round-tripは自己整合性しか測らない**。「外界の実装が受理するか」は別の検証軸として明示的に持つ必要がある。[[Patterns - 検証と調査#依存をモックした契約テストは、実際のランタイム統合を検証しない（2026-09-08）|モックした契約テストが実ランタイム統合を検証しない]]のと同じ構造——検証の環が系の内側で閉じている。
