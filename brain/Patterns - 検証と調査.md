## 移植の正解は、移植元を実際に実行するオラクルで取る（2026-09-27）

[[tecsgen-python3移植計画|tecsgen-python3]] P1で、Ruby版の挙動を「ソースを読んで写す」だけでなく、**移植元のソースをRubyで実行する小さなオラクル**（`tests/ruby/p1_oracle.rb`）を作り、同じ入力に対するRubyの結果とPython版を差分テストした。読んで写しただけのコードで、Float#to_sの指数表記への切り替え境界（`1.0e+15`は指数、`1234567890123456.8`は固定小数点）と、`String#sub`の置換文字列中`\k<名前>`が未定義名で例外になる挙動の2件を取り違えていたのが、オラクルで即座に見つかった。メッセージ表（約900件）も手で写さず、Rubyにソースをevalさせて JSON 経由で生成した。

**一般化**: 言語間移植で「同じ挙動」を保証したいとき、仕様書や目視での対応付けは言語組み込みの細かい規則（数値書式、正規表現置換、真偽判定）を取りこぼす。移植元の処理系がローカルで動くなら、①データ（表・リテラル）は移植元の処理系に解釈させて抽出し、②挙動は移植元を呼ぶオラクルとの差分テストで固定する。さらに、正解データを採った版（Ruby 3.2）と手元の版（Ruby 4.0）で書式が変わる機能（`Hash#inspect`）があるため、**オラクルも正解データと同じ版で一度は走らせる**（今回はWSLで実施）。[[Patterns - 検証と調査 Archive#他言語の一次資料を実際に読んで、仕様書の「inferred・未検証」フラグを解消する（2026-09-22）|一次資料を読む]]の一段先——読むだけでなく実行させる。

**再確認（2026-09-27、P2）**: 構文解析の駆動部を racc の Ruby 実装（`racc/parser.rb`）から写したところ、構文エラーの20ケースがすべてオラクルと食い違った。Ruby 版 tecsgen が実際に使っているのは racc の **C 実装**（`cparse.c`）で、エラー回復の挙動が違ったため（[[tecsgen-python3 構文解析方式決定]]）。読みやすい方の実装が「移植元」とは限らない。**移植元として読むのは、正解データを作った実行で実際に動いたコード**であり、それを確かめる手段もオラクル（両方の実装を実行して比べる）だった。

**再確認（2026-09-27、P3）**: モデル全体の比較では、オラクルが外部とのやりとり（ファイル存在判定・cpp 出力）も記録し、Python 側はそれを再生して Windows でもオフラインで回した。落とし穴は**同じコマンドが同じケース内で複数回呼ばれること**——記録をコマンド文字列をキーにした辞書にしたら後の呼び出しが前を上書きし、再生がずれた。外部呼び出しの記録は**呼び出し順の列**として持ち、順に消費する。また、ノイズ除去のフィルタが広すぎて `/usr/include` への問い合わせまで記録から落ちていた——除外は処理系自身のファイル（`/usr/lib/ruby/` 等）に限定する。

**再確認（2026-09-27、P5）**: `ThroughPlugin`系プラグインの重複防止キャッシュ（`@@generated_celltype`）が3インスタンス中1・2番目だけ`import(...)`行を出し3番目は出さない、という単純な「初回だけ出す」ロジックでは説明できない挙動が正解データに現れた。原因を確かめようと本物のRuby側に`STDERR.print "...#{@@generated_celltype[@ct_name].inspect}..."`というデバッグ出力を仕込んで再実行したところ、プロセスが数分経っても終わらずメモリを圧迫し続けた——原因は`inspect`が`Node`インスタンス（`@owner`等で巨大なASTグラフに循環参照でつながっている）を再帰的に文字列化しようとしたため。**移植元の実行系にその場で仕込む調査（デバッグprint等）は、対象言語の`inspect`/`to_s`が「小さい値」を前提に書かれているとは限らず、大きく相互参照したオブジェクトに対して呼ぶと机上の見積もりを超えて重くなりうる**——今回は実害の前にプロセスをkillして切り上げ、原因不明のまま「既知の小さな不一致」として記録するに留めた（[[tecsgen-python3移植計画]] P5b参照）。一方、`PluginModule.load_plugin`の2回目呼び出しが`P2001`ではなく`P2003`を返す、という食い違いは通常の差分比較（Python側の出力とゴールデンの出力を並べて読む）だけで原因を特定でき、修正できた——**「差分を読む」と「デバッグ出力を仕込んで再実行する」はコストが非対称で、後者は対象オブジェクトのサイズ・循環参照を確認してから使う**。

## 正解データで検証できない範囲は移植しない——先に正解データを採る（2026-09-28）

[[tecsgen-python3移植計画|tecsgen-python3]] P5h で「カーネル依存系プラグインに進む」段になって、対象を棚卸しすると HRP・HRP2・FMP・HRMP 系（約8,000行）と `ATK1EventPlugin`・`ATK1DelayTaskPlugin` は、正解データの155ケースに1件も使われていなかった。移植はできても Ruby 版との一致を確かめる手段がなく、これまでのフェーズで何度も「読んで写しただけのコードはどこかで食い違う」ことが確かめられている（[[#移植の正解は、移植元を実際に実行するオラクルで取る（2026-09-27）]]）。検証できる ATK1 の5本（`celltypePlugin` ケース）だけを移植し、残りは見送る判断をユーザーに提示して決定を得た（Multi 系・mruby 系でも、対象ケースのない `MrubyInfoBridge*` などは同様に見送り）。

**一般化**: 差分テストを受入基準にしている移植では、**「移植できるか」ではなく「一致を確かめられるか」で範囲を決める**。確かめられない範囲に手を付けると、見かけの進捗（行数）だけが増え、壊れていても誰も気づかないコードが積み上がる。対象を棚卸しするときは、ソースの行数と並べて「その機能を使うオラクルケースの数」を出す。ゼロなら、移植より先に正解データを採る（今回なら ASP3/HRP3 の CDL を WSL の Ruby 版に通してケースを足す）。着手範囲の選択肢は、検証可能性を明記してユーザーに示す。

## 移植済みで呼び出し元のない API は、初めて使うときに疑う（2026-09-28）

[[tecsgen-python3移植計画|tecsgen-python3]] P5i で `MrubyBridgeSignaturePlugin#new_cell` を移植すると、`Generator.parse` の移植（`CdlParser.parse_file`）がその場で書いた CDL を読めず `G1014` になった。P2 で移植済みだったが、これまで呼び出し元が一つも無く、差分テストを一度も通っていなかった。中身は、同じ役割の `Import`・`PluginModule.generate_and_parse` がホスト経由の読み込み関数（`_host_reader`）を渡しているのに、`parse_file` だけ既定の「実ファイルを直接読む」関数を使っていたというもの。テストの記録再生ホストでは、生成直後のファイルは実ファイルとしては存在しない。

**一般化**: 差分テストが緑でも、それは**実行された経路**についてだけの保証である。移植時に「後で使う」ために写した API は、呼び出し元が現れた時点で初めて検証される。新しい呼び出し元を書くときに食い違いが出たら、呼び出し側より先に「この API は今回初めて使われたのではないか」を確かめる（`grep` で呼び出し元を数える）。同じ役割の他の経路（ここでは Import）と引数・前提をそろえているかを比べると早い。

## Ruby の include を Python の多重継承に写すときは、mixin を親クラスより前に書く（2026-09-28）

[[tecsgen-python3移植計画|tecsgen-python3]] P5j で `OpaqueMarshalerPlugin` を移植すると、マーシャラの受け口関数が `SignaturePlugin` の素通し実装で生成された。Ruby の `class X < Base; include M` は祖先を `[X, M, Base]` の順に並べる（後から `include` したものほど前）ので、`M` のメソッドが `Base` に勝つ。Python で `class X(Base, M)` と親クラスから書くと MRO は逆になり、同名メソッドは `Base` が勝つ。P5d・P5e の `RPCPlugin`・`OpaqueRPCPlugin` も同じ書き方で、P5e で「未調査」と残した `opaqueRPC` の2ファイルの差はこれが原因だった（さらにその陰で、一度も呼ばれていなかった `gen_preamble` の書き誤りが見つかった。[[#移植済みで呼び出し元のない API は、初めて使うときに疑う（2026-09-28）]] の実例）。

**一般化**: Ruby の `include A; include B` は Python では `class X(B, A, Base)`（最後に `include` したものを先頭、親クラスを最後）と書く。クラス再オープンによる mixin（[[reference/Rubyクラス再オープンとpython対応|再オープン]]）は実クラスを最後に置く規約で既にそうなっていたが、プラグインの `include` は別の書き手が別の時期に写したため食い違った。移植した同名メソッドが「効いていない」ように見えたら、まず `X.__mro__` を Ruby の `X.ancestors` と並べて比べる。

## 網羅しているかは、出力の文字列検索ではなく、実行の計測で確かめる（2026-09-30）

[[tecsgen-python3移植計画 — P5 進捗ログ — P5j–P5k#P5k（2026-09-30）|tecsgen-python3 の P5k]]で、正解データが TECS のどのプラグインを実行したかを、プラグイン名を出力（標準出力・生成ファイルの名前と中身）から検索して調べたところ、39個が「痕跡なし」と出た。しかし移植済みで一致確認済みの `OpaqueMarshalerPlugin` や `MultiPlugin` が含まれていた。プラグイン名が出力に現れない経路（振り分け、内部だけで使う補助クラス）があり、文字列検索は、そこを静かに見落とす。

**一般化**: 「どこまで実行したか」を、成果物の文字列から逆算しない。実行側に計測を差し込んで直接数える。ここでは Ruby に `RUBYOPT=-r` でフックを差し込み、`load`/`require` したファイルと、基底クラスの子クラスのインスタンス生成を記録した。集計は「一度もロードされない（＝正解データが無い）」と「ロードされたが生成されない（＝基底・振り分け用で抜けとは限らない）」を分け、判定の限界（ロードと生成の有無だけで、全分岐は見ない）も報告に書く。全件を2回実行して報告が同一であることを確かめ、採取結果は捨てる場所（リポジトリの外）に出す。計測用の道具（フック・実行スクリプト・集計）は、次回も同じ手順で回せるようリポジトリに入れた。

## Ruby 版の癖は、直さず再現する — 一致は「正しさ」ではなく「同じ振る舞い」で測る（2026-10-01）

カーネル依存プラグインの移植（P5l〜P5p）で、正解データに出ている Ruby 版の癖を、直さずにそのまま書いて一致させた例: ブロック内で初めて代入した局所変数は周回ごとに nil に戻る（`FMPObjectPlugin#gen_factory` の `indent`。2セル目以降にインデントが出ない）、String の `"root"` と Symbol の `:root` は等しくない（クラス名の比較）、`print nil` は何も出さない、`Object.const_defined?` は「読み込み済みのクラスか」（`Notifier` がドメインプラグインを選ぶ手順）、`plClass.class.name` は `Class`、`"plClass.name}"` のように `#{` が欠けた文字列がそのまま出る。移植元に明らかなバグがあっても、正解データがそう出力している限り直さず、Python では `Symbol`（`str` の派生で等値を区別）や `to_s` で同じ結果にする。**手順**: ①比較は `p4_progress.py -v -d` の差分で見る（生成物が全一致で標準出力だけ違えば、`make` の表示や `-v` の文言を疑う）、②差分の出た行から Ruby のソースを引く、③直したら全件を再実行して後退が無いことを確かめる。
