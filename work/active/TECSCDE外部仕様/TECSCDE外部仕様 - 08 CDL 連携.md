## 8. CDL 連携

第5章がファイル操作の手続き（いつ読み書きするか）を扱ったのに対し、本章は変換の中身（CDL の何が図の何に対応するか、図から書き出した CDL を tecsgen がどう扱うか）を扱う。現行版の事実は、TECSCDE が解析処理を一切自前で持たず tecsgen をライブラリとして内部に抱えている点に基づく。一次資料は起動処理 `tecsgen.rb`、解析処理 `tecslib/core/tecsgen.rb`（`syntax_analisys`・`semantics_analisys_1/2`・`run1`・`run2`）、`Import` クラス（`tecslib/core/componentobj/import.rb`）、および `direct_import` の読み書き（`cdelib/saveload.rb`・`tecslib/core/tool_info.rb`）である。

### 8.1 CDL インポート（CDL → 図）

#### 8.1.1 現行版の動作

TECSCDE 自身は CDL を解析しない（5.3.1 で既述）。起動は tecsgen 自体の起動体系をそのまま流用しており、コマンドライン引数 `ARGV` 全体が `syntax_analisys(argv)` に渡される。`argv` の各要素は**例外なくすべて** `Import.new( f, false, false )` としてインポート登録される（`tecslib/core/tecsgen.rb` 232〜235行）。順序に特別な扱いはなく、「どれが編集対象か」は別の場所（`add_cell_list_from_tecsgen` の `argv[-1]`、5.3.1 で既述）で後から決まるだけである。

CDL 内の `import`／`import_C` 文も同じ `Import` クラスに登録されるが、こちらは `b_imported` が既定の `true` のままである（`bnf.y.rb` 847〜849行）。すなわち**インポートの記録は起点の異なる2種類が同居している**。

| 起点 | `b_imported` | 契機 |
|---|---|---|
| コマンドライン引数として直接指定 | `false` | 起動時の `ARGV` の各要素（`tecslib/core/tecsgen.rb` 234行） |
| CDL 文中の `import`／`import_C` 文 | `true`（既定） | 構文解析中に文を読んだとき（`bnf.y.rb` 847〜849行） |

後者のうち `import_C` は、取り込む C ヘッダを実際に外部の C プリプロセッサ（既定 `gcc -E -DTECSGEN`、`$cpp`）へ渡して展開する（`tecslib/core/componentobj/import_c.rb` 169行）。セルタイプ・シグニチャの定義もこの解析経路で読み込まれるが、図には現れない（4.2.1・4.5.1 で既述）。複合セルタイプは構文としては解釈されるが、図のモデルには一切反映されない（4.7.1）。

#### 8.1.2 JS 版の規定

- 5.3.2 で定めた解析対象（`cell` 定義・`__tool_info__` ブロック）を本節で確定する。**セルタイプ・シグニチャの定義ブロックも読み取り専用の解析対象に含める。** 4.2.2・4.5.2 が「読み込んで参照するのみ」とした前提には、セルのポート構成を描画するためにセルタイプ定義自体を読む必要があることが暗に含まれており、本節で明示する。
- `import`／`import_C` 文は 5.3.2 のとおり追跡しない。**`import_C` が要求する C プリプロセッサの実行は、ブラウザ単体構成（2.2「依存ライブラリなし」）と両立しないため、常に非対応とする。** `import_C` で取り込まれるはずだった C ヘッダ由来のセルタイプ・シグニチャは、5.3.2 の「セルタイプが解決できない」と同じ扱い（未解決として警告）に倒す。
- コマンドライン引数による複数ファイル同時指定（`argv` 全体をインポート登録する現行版の起動体系）に相当する機能として、**ファイル選択・ドラッグ＆ドロップ（5.3.2）を複数ファイル対応に拡張する。** 複数選択時は現行版の `argv[-1]` 規則を踏襲し、**最後に選択（またはドロップ順で最後）したファイルを編集対象とし、他は参照専用として読み込む**。参照専用ファイルで定義されたセルは、5.3.2 の編集可否規則（定義元ファイルで決まる）に従い編集不可として扱う。

### 8.2 CDL エクスポート（図 → CDL）

#### 8.2.1 現行版の動作

5.1.1 で確定したとおり、保存＝CDL エクスポートであり別機能ではない。本節では 5.4.1 が簡潔に触れた `direct_import` の生成規則を確定する。

`save_tecsgen`（`saveload.rb` 522〜530行）は `Import.get_list` から**`is_imported?` が偽（＝コマンドライン引数として直接指定された）かつ編集対象ファイル自身ではない**エントリの `get_cdl_name` を列挙する。すなわち `direct_import` が保存するのは**CDL 内の `import` 文で取り込まれたファイルではなく、起動時にコマンドライン引数として編集対象と一緒に渡された「兄弟ファイル」の一覧**である——8.1.1 で見た2種のインポート起点のうち①（コマンドライン直接指定）のみが対象で、②（CDL 内 `import`／`import_C` 文）は保存対象に含まれない。②は書き出す `cell` ブロック中の `import` 文としてそのまま CDL テキストの一部に残る。

読み込み時、`tool_info.rb`（110行）は保存された `direct_import` の各パスを `Import.new( import, false, false )` として再登録する——コマンドライン引数として再度渡されたときと**寸分違わぬ状態**を復元する。これにより「兄弟ファイル」由来のセルタイプ解決が再現される。書き出す `cell` ブロックの対象は編集可能なセルのみである（5.4.1 で既述）。

#### 8.2.2 JS 版の規定

- 5.4.2 で規定した保存操作（直近の保存先への書き戻し／名前を付けて保存）が生成する内容を本節で規定する。**`direct_import` に相当するフィールドは、8.1.2 で新設した「参照専用ファイル」の一覧（ファイル名のみ）として書き出す。**
- **現行版のような解決済みインポートグラフからの逆算は行わない。** JS 版のパーサは `import`／`import_C` 文を追跡しないため（8.1.2）、どのファイルが直接指定でどのファイルが間接的に取り込まれたかを判別する材料を持たない。したがって direct_import 相当のフィールドは、常に「今回のセッションで利用者が明示的に参照専用として読み込んだファイル」の記録に限定する——8.1.1 の②（CDL 内の `import` 文経由）に相当する情報は生成しない。
- 再読み込み時、参照専用ファイルの一覧はファイル名の提示に留まる。**ブラウザはファイルシステムへの継続的なアクセス権を持たないため、現行版のような自動的な再解決はできない**（File System Access API 利用時を除く、5.4.2 で既述）。利用者に再度ファイル選択を促す。
- CDL 内の `import`／`import_C` 文自体は、5.3.2 のとおり解析するが追跡しないため、**入力時の生テキストのまま書き戻す**（5.1.2 で `base_dir`・`import_path`・`cpp` について定めた「解釈せず保持する」方針と同一）。

### 8.3 整合性チェック（図と CDL の差分検出）

#### 8.3.1 現行版の動作

現行版に、図と CDL の整合性を明示的にチェックする機能は存在しない（`cdelib` 全9ファイルに `consisten`／`verify`／`diff` に相当する処理はなく、`tmodel.rb` 1079〜1092行の配列添字チェックが唯一の近い処理だが、これは図内部のポート配列の添字重複チェックであり CDL との突合ではない）。

実質的な整合性の扱いは、読み込み時（5.3.1）とレイアウト復元時（5.5.1）に暗黙かつ個別に行われる——セルタイプ未解決は黙って読み飛ばし、レイアウト不整合は黙って自動配置に戻す。**利用者が「今の図とファイルはどこがずれているか」を一望する手段はない。**

#### 8.3.2 JS 版の規定

現行版に前例がないため、本節は新規要件として規定する（6.7・6.8・7.4 と同じ位置付け）。

- 利用者が任意のタイミングで実行できる「整合性チェック」操作を追加する。実行すると、5.3.2・5.5.2・8.1.2 で個別に警告として提示していた項目（セルタイプ未解決・結合先不在・複合セルタイプ・レイアウト不整合・参照専用ファイル未解決）を**1件のレポートとして集約表示**する。9章で規定するメッセージ形式に従う。
- レポートの各項目は対応する図の要素へのジャンプを持つ。**7.4 で規定した検索ハイライトの巡回機構をそのまま流用する**——専用の強調表示を新たに設計しない。
- **ファイルの再取り込みによる差分検出を追加する。** 参照専用ファイル（8.1.2）を利用者が再選択した場合、前回読み込み時点のセル定義と比較し、追加・削除・変更されたセルタイプを差分として提示する。これは現行版が持たない、外部で CDL が編集された場合に対応するための機能である。
- **整合性チェックは、tecsgen が実際にこの CDL を受理するかどうかを保証しない。** 本ツールが検出できるのはモデルの構文的・参照的な整合性に限られ、CDL の意味論的な正しさ（型検査等）は 8.4 で述べるとおり tecsgen 自身の役割のままである。

### 8.4 tecsgen との連携（コード生成トリガー）

#### 8.4.1 現行版の動作

**現行版はコード生成を一切トリガーしない。** `@tecsgen` として内部に抱えているのは `syntax_analisys` → `semantics_analisys_1` → `semantics_analisys_2` からなる `run1` 相当の解析処理のみであり（`tecslib/core/tecsgen.rb` 240〜252行）、コード生成を行う `run2`（`optimize_and_generate` → `finalize`、254〜261行）は `cdelib` 全9ファイルのどこからも呼ばれない（`run1`／`run2`／`optimize_and_generate` を grep してもゼロ件）。パレット（3.3.1）にも Generate・Build に相当するボタンは存在しない。

したがって**現行版でもコード生成は完全に利用者の手作業**である——TECSCDE で編集・保存した `.cde`（実体は CDL、5.1.1）を、利用者が別途コマンドラインから `tecsgen` に渡す。TECSCDE は CDL を読み書きする設計環境（1.2「ツールチェーンにおける位置付け」で既述）であり、この境界は現行版の時点で既に確定していたことになる。

唯一の間接的な連携は `__tool_info__("tecsgen")` に保存される `base_dir`・`import_path`・`define_macro`・`cpp`（5.1.1）である。これらは tecsgen 起動時に必要なコマンドラインオプションそのものだが、**再生成に使うのは利用者であり TECSCDE ではない。**

#### 8.4.2 JS 版の規定

- **2.3 で定めた「tecsgen を直接起動できない」制約は、現行版からの後退ではなく、現行版の設計をそのまま引き継ぐものである。** 現行版がコード生成をトリガーしていた実装から JS 版で機能を落とすのではなく、元々存在しなかった機能を新設しないだけであることを明記する。
- **生成コマンドの提示を新規に追加する。** `__tool_info__` に保持している `base_dir`・`import_path`・`define_macro`・`cpp`（5.1.2 で解釈せず保持すると規定済み）と、8.1.2 で新設した参照専用ファイル一覧から、利用者がローカル環境でそのまま実行できる `tecsgen` のコマンドライン（例: `tecsgen -I <base_dir> -D <macro> <参照専用ファイル…> <編集対象ファイル>`）を組み立てて表示し、コピーできるようにする。実行はしない——2.3 の制約の範囲内で、tecsgen 連携を「代行」ではなく「補助」として提供する。
- **tecsgen が実際にこの CDL を受理するかどうかを、本ツールは保証しない。** 8.3 の整合性チェックは構文的・参照的な整合性に限られ、tecsgen 側の意味解析（型検査・重複定義検出等）を代替しない。生成コマンド提示の直後に「実行結果は tecsgen 自身のエラー出力を確認すること」という一文をあわせて表示する。
- ツールバージョンの整合性（2.1 の tecscde V0.5.1 ／ tecsgen V1.3.1.0 以降という対応関係）についても、JS 版は実行時に確認する手段を持たない。`cde_format_version` の版数チェック（5.1.2 で規定済み）が担える範囲に留め、tecsgen 本体のバージョンチェックは利用者の責任とする。
