 `\docs\from_source\spec\external\*.md` を参照したうえで、`\docs\from_source\spec\external\.md` の矛盾点をすべて列挙して。

============================================
docs/from_source/spec/internal/**/*.md を横断的に確認しました。util_yaml.md を参照する他の仕様書（index.md, db/db_yaml.md, db/storex.md, common/util.md, tomlop/tomlop.md）とは矛盾はありません（db_yaml.md 37行目が「UtilYaml._register_constructors でカスタムタグを無害化登録したうえで yaml.safe_load」と記述しており、実際の呼び出しコード db_yaml.py 51〜52行目と一致）。util_yaml.md 単体の内部に、ソース src/yklibpy/common/util_yaml.py と突き合わせて矛盾点が1つ見つかりました。

矛盾点

_register_constructors の処理フローで、実際は同一の if 文の中にある2つの操作を、片方だけ条件付き・もう片方は無条件であるかのように分けて記述している

30〜35行目:
処理フロー:
  1. tags に "tag:yaml.org,2002:python/object" を追加する
  2. 未登録（_constructors_registered が False）であれば、各タグに ignore_python_object_tag を SafeLoader へ登録する
  3. 登録済みフラグを True にする（登録の有無に関わらず毎回 True を再設定）

この書き方は、ステップ1（tags への追加）が無条件に毎回実行され、ステップ2（yaml.add_constructor での登録）だけが _constructors_registered の状態によって条件付きであるかのように読めます。

しかし実装（util_yaml.py 28〜37行目）では、tags.append("tag:yaml.org,2002:python/object") は for tag in tags: ループとまったく同じ if not cls._constructors_registered: ブロックの中にあります。つまり _constructors_registered が既に True（2回目以降の呼び出し）の場合、tags への追加も yaml.add_constructor への登録も両方ともスキップされ、渡された tags リストは一切変更されません。

これは実際に問題になる箇所です。db_yaml.py（51行目）の load() は呼び出しのたびに新しい tag_list = tags or [] を作って UtilYaml._register_constructors(tags=tag_list) を呼んでいますが、プロセス内で一度でも _register_constructors が実行されると _constructors_registered はクラス変数として True のまま残るため、2つ目以降の DbYaml インスタンスの load() 呼び出しでは、たとえ別のカスタムタグ一覧を渡しても、それらのタグは一切登録されず無視されます。この重大な帰結は「設計上の注意」（65行目、グローバルな副作用への言及）でも触れられておらず、処理フローの記述自体も実態（2つの操作が同じ条件で一体不可分である）と食い違っています。

補足（矛盾とまでは言えない、軽微な点）

safe_load（37〜39行目）で説明されているメソッド UtilYaml.safe_load は、src/ 全体を検索しても呼び出し箇所が一つも存在しません。カスタムタグ登録後に実際に YAML を読み込んでいる唯一の箇所（db_yaml.py 52行目）は UtilYaml.safe_load ではなく PyYAML の生の yaml.safe_load を直接呼んでおり（db_yaml.md 37行目もそう記述している）、UtilYaml.safe_load は事実上デッドコードです。ただし util_yaml.md 自身はこのメソッドが「使われている」とはどこにも主張していないため、直接の矛盾ではなく未配線状態の指摘に留まります。

docs/from_source/spec/internal/**/*.md を横断的に確認しました。index.md（38行目）も同じ表現「辞書ベースのストレージ実装が共有する基底クラス」を使っており、db_yaml.md（4, 26, 87行目）は DbYaml が DbBase.__init__() を呼び出す旨を正しく記述しています。ソース src/yklibpy/db/db_base.py（6行）・db_yaml.py と突き合わせたところ、db_base.md 単体の内部（概要と設計上の注意の間）に矛盾点が1つ見つかりました。

矛盾点

概要の「DbYaml 等が共有する基底クラス」という記述が、実際には唯一の派生クラスに対してすら「共有」も「実用」もされていない事実と矛盾している

8行目（概要）:

▎ 辞書ベースのストレージ実装（DbYaml 等）が共有する基底クラス。空の連想配列を保持するだけの最小構成。

「DbYaml 等」という表現は、複数の辞書ベース実装クラスがこの基底クラスを共有しているかのように読めます。しかし src/ 全体を検索すると DbBase を継承しているクラスは DbYaml の1つだけで、「等」に該当する他の実装は存在しません。

さらに36行目の「設計上の注意」自身が次のように述べています。

▎ assoc は基底クラスで初期化されるのみで、DbYaml は独自に data という別の辞書を持ち assoc を直接使っていない。...実質的に未使用のフィールド

つまり、唯一の派生クラスである DbYaml でさえ DbBase が提供する状態（assoc）を一切使っていません。8行目の概要は「共有する基底クラス」として実用的な抽象化であるかのように描写していますが、36行目の設計上の注意はそれを「実質的に未使用」と否定しており、同一ファイル内で「共有され実際に使われている」という印象と「実質未使用」という実態が矛盾しています。「等」という語も、唯一の（かつ機能を使っていない）継承者しか存在しない実態と食い違っています。

docs/from_source/spec/internal/**/*.md を横断的に確認しました（index.md, db_base.md とは矛盾なし）。ソース src/yklibpy/db/db_yaml.py・db_base.py と突き合わせたところ、db_yaml.md に矛盾点が1つ見つかりました。

矛盾点

概要が「get_or_create_db("yaml", fname) 経由で生成されることを想定している」と述べているが、そのような関数はコードベースのどこにも存在しない

8行目（概要）:

▎ YAML ファイルを背後ストアとして扱う簡易 DB 実装。辞書形式のデータをメモリ上に保持し、必要に応じて YAML ファイルと相互変換する。get_or_create_db("yaml", fname) 経由で生成されることを想定している。

get_or_create_db という関数・メソッドを src/ 全体（および docs/from_source/spec/internal/**/*.md 全体）で検索しましたが、この1箇所にしか出現しません。実装（db_yaml.py）を見る限り、DbYaml は単純にコンストラクタ DbYaml(fname) を直接呼んで生成されており、それをラップするファクトリ関数は現状のコードベースに存在しません。

つまりこの記述は、実装から検証できない（存在しない関数への）参照であり、実際の生成経路（直接インスタンス化）と矛盾しています。過去に存在した、または将来追加予定のファクトリ関数を指している可能性はありますが、現状のソースコードとは整合していません。

その他（インスタンス変数・各メソッドの説明とフロー・依存表・「設計上の注意」2点、特に sys.argv > 1 の条件が逆転しているという指摘）はすべてソースコードと一致しており、正確でした。
