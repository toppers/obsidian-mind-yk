# ops-structure-review
# 分散資産の運用構造レビュー (ops-structure-review)

複数環境(Claude / Claude Code / Codex / Obsidian)に分散した仕事資産の運用構造をレビューする。目的はファイルを直すことではなく、運用上の改善点(混在・矛盾・重複・陳腐化・漏洩リスク・役割分担の崩れ)を判断材料として出すこと。

## 大原則

- **実物を読んでから書く。** 推測で断定しない。読めたものと読めなかったものを厳密に分ける。
- **読めていないものは「要確認」と明記する。** このスキルの実行環境からは対象の大半が見えないことが多い(下記スコープ表)。見えない領域について診断をでっち上げず、レビューに載せる具体的な方法(アップロード or 該当環境での再実行)を提示する。
- **ファイルの編集・削除・記憶編集の変更は一切しない。** 出力は診断レポートのみ。修正はユーザーの承認後、別タスクとして行う。
- **抽象的な助言は書かない。** 各指摘には実測した事実(ファイル名・行・日付・実行コマンドの結果)を添え、確認方法まで書く。

## 手順

### 0. スコープ確定(最初に必ず実行)

実行環境ごとに読める範囲が違う。何が読めて何が読めないかを最初に確定し、レポート冒頭に明記する:

| 実行環境 | 読める | 読めない(要確認) |
|---|---|---|
| claude.ai(Project外) | ユーザーSkill(`ls /mnt/skills/user/`)、記憶+記憶編集(view)、Project外チャット、uploads、接続済みDrive | Project内一式、ローカルの CLAUDE.md / AGENTS.md / Obsidian vault |
| claude.ai(Project内) | 上記+当該ProjectのKnowledge・指示・Project内チャット | 他Project、ローカル一式 |
| Claude Code / Cowork | ローカルファイル全般(CLAUDE.md、`.claude/`、AGENTS.md、Obsidian vault のパスが分かれば) | claude.ai側の記憶・Project |

読めない領域は「要確認」とし、(a) 該当ファイルをzipでアップロードしてもらう、(b) 該当環境で同じレビューを再実行してもらう、のどちらかを具体的に案内する。両環境の結果が揃って初めて観点3(環境間矛盾)と観点4(重複)が完全に判定できる。

### 1. 実物調査

読める範囲を以下の順で調べ、証拠を記録する:

1. ユーザーSkill一覧と各SKILL.md。参照するスクリプト・同梱ファイルの実在を `ls` で検証する
2. 記憶本文と記憶編集(view)。**反映済みの一回性修正指示が残骸として残っていないか**、適用先が現存するかを確認する
3. 過去チャット(`recent_chats` / `conversation_search`)。検索スコープ(Project内外)をレポートに明記する
4. uploads と接続済みDrive(「AGENTS」「CLAUDE.md」「棚卸」「確認待ち」等で検索)
5. **宣言と実体の照合(このスキルの中核)**: 記憶・チャット記録が「作成した/統合した/廃止した」と主張する資産が、実体(インストール済みSkill一覧、ファイルシステム)と一致するか突き合わせる。この環境ではSkill反映に手動アップロードが必須のため、「編集した」と「反映されている」の間の断絶が頻出する

### 2. 8観点での評価

該当なしの観点は「確認範囲になし」、読めない観点は「要確認」と書く:

1. **確認待ちと正式記憶の混在** — 暫定メモと確定ルールが同じ場所にないか。Claude側では「Skill化したつもりのルールが揮発性の記憶本文にしかない」状態もこれに含む
2. **陳腐化** — 古い価格、仕様、UI手順、公開方針。日付併記のない実測値・人気度指標も予備軍として指摘する
3. **環境間矛盾** — AGENTS.md、CLAUDE.md、Skills、Obsidian記憶の間の指示の食い違い。宣言と実体の乖離もここに含む
4. **重複** — 同じ役割のファイル・ルールの多重管理。同一メタルールのSkill間コピーは、相互参照不能な仕組み上の意図的冗長化かを判別してから指摘する
5. **死蔵ルール** — 今は使っていない古い運用ルール。使用実績が確認できないものは「使用実績要確認」とする
6. **漏洩リスク** — 機密情報、クライアント名、APIキー、内部URLが公開向け文面に混ざる経路
7. **棚卸し設計** — 日次・週次・月次で拾うべき情報が定義・整理されているか
8. **役割分担** — 考える場所・作業する場所・記録する場所の分離が崩れていないか

### 3. レポート出力

冒頭に「読めたもの(実測一覧表)/読めなかったもの(要確認)」を置き、続けて:

```
1. 全体評価
2. 最も危ない運用上の問題
3. 矛盾している可能性があるルール
4. 古くなっていそうな情報
5. 重複・肥大化している領域
6. 改善した方がいいフォルダ構造または命名ルール
7. 今すぐやる3つ(投資対効果順・各所要時間つき)
8. 本人に確認すべきこと(番号つき・yes/noで答えられる形)
```

各セクションの改善案には**「今すぐ直すもの」「保留でよいもの」「本人確認が必要なもの」**のいずれかを必ず付す。

## レポート後のフォロー(ユーザーが回答してきた場合)

- 回答で確定した事実は、一回性の修正指示ではなく**恒久的に真である事実の形**で記憶編集に反映することを提案する(例: 「Xは廃止済み(2026-07確定)」)。修正指示形は反映後に残骸化する
- 記憶編集の削除は降順(大きい番号から)で行い、実行後にviewで最終状態を確認する
- 不採用と決まった資産に運用ルールが含まれていた場合、その置き場(userPreferences / 記憶編集 / Obsidian)を確認し、揮発性の記憶本文にしか残らない状態を放置しない
