- 1.説明型
	- 特定のライブラリ、CLI、SDKの正しい使用方法を説明するために用いられる
	- 例
		- `billing-lib`は内部課金ライブラリのエッジケースと回避策
		- `internal-platform-cli`は内部CLIラッパーの各サブコマンドの例示
		- `sandbox-proxy`は開発作業用のエグレスゲートウェイ設定、「接続拒否」エラーのデバッグ、ホワイトリストエントリの追加などに対応
- 2.検証型
	- コードが正常に動作するかのテストや検証方法を記述し、多くの場合PlaywrightやTmuxなどの外部検証ツールと連携する
	- 例
		- `signup-flow-driver`（ヘッドレスブラウザで「登録→メール確認→オンボーディング」を実行し、各ステップで状態をアサート）
		- `checkout-verifier`（Stripeのテストカードで決済UIを操作し、請求書の状態を検証）
		- `tmux-cli-driver`（TTYが必要なインタラクティブCLIのテスト用）
- 3.データ・監視接続
	- エージェントをデータおよび監視技術スタックに接続する
	- この種のスキルには、認証情報付きのデータ取得ライブラリ、特定のダッシュボードID、ワークフローやデータ取得方法の説明が含まれることがある
	- 例
		- `funnel-query`は登録、アクティベーションから課金までのイベントを関連付け、標準的な`user_id`を含むテーブルを提供
		- `cohort-compare`は2つのグループのリテンションまたはコンバージョンを比較し、統計的に有意な差をフラグ付けする
		- `grafana`と`datadog`は、データソースUID、サービスリスト、フィールドプレフィックス、およびフィールドの意味的な違い（例：`@request_id`と`trace_id`）に対応
- **4.自動化・依存関係オーケストレーション型**
	- 反復的なワークフローを単一のコマンドに圧縮
	- チームは、以前の結果をログファイルに保存することで、モデルの一貫性維持と過去の実行に対する振り返りを支援することを推奨
	- 例
		- `standup-post`（チケットトラッキング、GitHubのアクティビティ、以前のSlackメッセージを集約し、増分変更のみのデイリースタンドアップレポートを生成）
		- `create-<ticket-system>-ticket`（スキーマ仕様を強制し、後続のリマインダーとSlackリンクをトリガー）
		- `weekly-recap`（週次レポート投稿の生成）
- **5.コードスキャフォールディング/ジェネレーター型**
	- コードベースの特定機能向けにフレームワークのボイラープレートコードを生成
	- 例
		- `new-<framework>-workflow`（カスタムアノテーションに従って新サービス/ワークフロー/ハンドラのスキャフォールディングを生成）
		- `new-migration`（データベースマイグレーションのテンプレートと一般的な大きな落とし穴を提供）
		- `create-app`（認証、ログ、デプロイ設定が事前構成された内部アプリケーションを作成）
- **6.コード品質・レビュー補助型**
	- 組織内でコード品質基準を強制し、コードレビューを支援
	- チームは、これらのスキルには決定論的なスクリプトやツールを含めることができ、堅牢性を目標とし、フックとして、またはGitHub Actionで自動実行できる
	- 例
		- `adversarial-review`（「批判的な傍観者」サブエージェントを派生させ、反復的に批判と修正を行う）
		- `code-style`（コードスタイルを強制、特にClaudeのデフォルト動作が不十分な部分）
		- `testing-practices`（テストの作成と重点項目に関する具体的なガイドを提供）
- **7.異常調査/レポート生成型**
	- Slackのスレッド、アラート、エラーシグネチャなどの異常現象を入力とし、複数のツールを用いて段階的に調査し、最終的に構造化されたレポートを生成
	- 例
		- `<service>-debugging`（異常現象を対応するツールとクエリパターンにマッピング）
		- `oncall-runner`（アラートを取得→一般的な調査ポイントをチェック→出力をフォーマット）
		- `log-correlator`（指定されたリクエストIDに基づき、各システムから一致するログを抽出）
- **8.日常保守・ガードレール型**
	- 破壊的な操作を伴うプロセスには、エンジニアの重要な操作がベストプラクティスに従うように、より強力なガードレール（Guardrails）が必要
	- 例
		- `<resource>-orphans`（孤立したPod/ボリュームを検索し、Slackに投稿してユーザー確認と観察期間を経てからカスケードクリーンアップ）
		- `dependency-management`（依存関係の承認ワークフロー）
		- `cost-investigation`（ストレージ/エグレストラフィック費用の急増について、バケットとクエリパターンを含めて原因を特定）
- 9.**ベストプラクティス・反復型**
	- スキルに関連する方法論そのものであり、全てのカテゴリに共通
	- チームがスキルのベストプラクティス、ヒント、コツをまとめることは、本質的にスキルをエッジケースと共に成長させることと等しい
	- 優れたスキルは多くの場合、「少数の行と一つの小さな落とし穴のヒント」から始まり、チームが新たなエッジケースに遭遇するたびに拡張され、徐々に完成度を高めていくことが強調
- どのよにl書くか
	- スキルを「Claudeがデフォルトで行うことを単に繰り返すだけ」にしないこと
		- チームは、スキルがモデル本来の能力を復唱するだけなら、コンテキストの負荷を増やすだけで価値を生まないと指摘
	- 「情報密度が最も高い部分」をGotchasに置き、Claudeがそのスキルを使用する際の一般的な失敗点に基づいて継続的に更新する
	- `SKILL.md`を利用して他のファイルを指し示し、スキルに「段階的提示（Progressive Disclosure）」を形成させる
		- チームは、ファイルシステムをコンテキストエンジニアリングの一部として扱い、どのファイルをいつ読み取るべきかを、適切なタイミングでエージェントに探索させることを推奨
		- 例
			- ジョブが保留状態にある場合は`stuck-jobs.md`を参照
			- 詳細な関数シグネチャと使用例は`references/api.md`に分割
			- 最終出力がMarkdownファイルの場合は`assets/`にテンプレートを配置してコピーして使用できるようにする
	- 指示に適度な柔軟性を持たせる
		- 例
			- ユーザーコンテキストを必要とするスキルの場合、チームは設定情報を`config.json`に格納し、設定が未完了の場合にのみ、エージェントがAskUserQuestionツールを使って構造化された方法で質問することを推奨
	- フックとセッション内メモリによって一貫性を高める
		- スキルには「呼び出し時にのみアクティブ化され、現在のセッションでのみ持続する」フックを含めることができる
		- 例
			- `/careful`は`rm -rf`、`DROP TABLE`、force-push、`kubectl delete`をインターセプトできる。
			- `/freeze`は指定ディレクトリ以外への変更書き込みをインターセプトし、デバッグ中の誤った修正を防ぐ
	- スキルの配布メカニズム
		- コードベースの`./.claude/skills`にチェックインするか
		- プラグインとして作成し
		- Claude Codeプラグインマーケットプレイスを通じてアップロード・インストール
		- チームは中央集権的な承認を行わず、「最も実用的なスキルが自然に浮上する」ことを重視
			- 誰かがまずGitHubのサンドボックスにアップロードしてSlackなどのチャネルで推薦し、注目を集めた後にPRを提出して公式マーケットプレイスに登録される、という流れだ。
	- エージェントを使ってコードを書く場合のリターンは、「プログラミングの基礎能力」とは正の相関関係になく、むしろタスクにおけるユーザーの「計画と実行の分担」の把握に依存していることが判明
		- 人間は主に「何をするか」（計画系の意思決定）を決定し、エージェントは主に「どのように行うか」（実行系の意思決定）を決定する。
	- 「スキルには正しいアーキテクチャが必要であり、特にGotchasと受け入れルールを明確に記述すべきである」
	- エージェントが文法、ボイラープレート、実行の一部を自動化できるようになると、ユーザーが要件を明確に伝え、タスクを実行可能なチェーンに分解し、結果を検収できるかどうかが、アウトプットの品質を決定するより重要な変数に近づく。
	- 本質的には「エンジニアリング資産化」への道筋である。経験をトリガー可能なディレクトリ、スクリプト、設定フックとして蓄積し、マーケットプレイスやコードベースへのチェックインを通じてチーム内に拡散させる。
	- スキルのベストプラクティスを実行する上では、検証スキルとGotchasの継続的な更新が特に重要である。チームは「1週間かけて検証スキルを徹底的に作り込むことは非常に価値がある」と明言しており、これはエージェントプログラミングが「生成」から「工学的なデリバリー」へと移行する際に、テストと制約に対する要求がより高まっていることを反映している。
